# Renoir DAX static-v1 — 실측 전 1차 스피커 후보

작성: 2026-10-23. 사용자 요청에 따라 현재 정적 분석만으로 적용한다.
Mi 11 Lite 5G의 TFA9873N1B 대상 컨테이너와 Redwood AW 드라이버·DTS 비교를
근거로, Redwood의 채널별 양수 증폭을 그대로 이전하지 않는 출발점을 택했다.
renoir 주파수 응답을 측정해서 계산한 보정 곡선은 아니다.

## 적용 정책

`speaker_landscape`의 optimizer `gain_left/right`에만 `min(원본, 0)`을 적용한다.
13개 gain, 9개 밴드가 바뀐다. 기존 감쇠는 풀지 않으며 L/R을 교환하지 않는다.
세로 프로필, 사용자 GEQ, 헤드폰, 저역·regulator·MBDRC·limiter 관련 설정과
TFA 컨테이너·ACDB·캘리브레이션은 변경하지 않는다.

이는 raw optimizer 제어값의 감소다. 다른 동적 처리·필터 보간을 포함한 실제
음압 감소나 보호 동등성을 수학적으로 보증하지 않는다. 고역이 덜 선명하거나
답답하게 들릴 수도 있으며, 청취와 측정으로 평가해야 한다.

| 주파수 Hz | 원본 L / R | static-v1 L / R |
|---|---|---|
| 1313 | 16 / -16 | 0 / -16 |
| 1688 | 16 / -16 | 0 / -16 |
| 3000 | 6 / -36 | 0 / -36 |
| 5813 | 16 / -17 | 0 / -17 |
| 7125 | 48 / 16 | 0 / 0 |
| 9000 | 80 / 40 | 0 / 0 |
| 11250 | 95 / 14 | 0 / 0 |
| 13875 | 91 / 56 | 0 / 0 |
| 19688 | 16 / -16 | 0 / -16 |

표의 gain은 원시 정수값이며 dB 표기가 아니다. 표에 없는 밴드는 그대로다.

## 재현과 빌드 연결

- 원본 SHA-256: `d7e21ddb0f9d58330b655dd120799b3db46428f6840f87e707239644693a1a9c`
- 후보 SHA-256: `84abb44348ab88ec97adfcc742f27ec8b8ddf69316921d7b2d61728ae9a4205e`
- 원본 `proprietary/vendor/etc/dolby/dax-default.xml`은 계속 Redwood 추출본이다.
- `tools/gen-renoir-dax.py`는 원본 hash를 검사하고 허용된 변경만 생성한다.
- Soong genrule `renoir_dax_static_v1`이 후보를 만들고 기존
  `dolby-dax-default.xml` 모듈이 **기존 설치 경로**에 설치한다.
- 원본 보존으로 추출/재추출 시에도 pin 검증이 유지된다. 파서나 blob 자체를
  변조하지 않으며 후보 전체 XML을 Git에 재배포하지 않는다.

도구로 직접 생성한 후보와 빌드 산출물은 같은 입력·정책에서 같은 해시여야 한다.
검증 범위는 Python 실행/변경 범위 검사와 Blueprint 구문이다. 이번에는 ROM 또는
제품 모듈 빌드를 실행하지 않았다. 실제 Soong 의존성 해석·설치는 미검증이다.

복원하려면 `Android.bp`의 `dolby-dax-default.xml` 모듈에서 다음 한 줄을 되돌린 뒤
사용자가 다시 빌드한다. 원본 blob은 남아 있으므로 재추출할 필요가 없다.

```bp
src: "proprietary/vendor/etc/dolby/dax-default.xml",
```

현재 값은 `src: ":renoir_dax_static_v1"`다. 파일을 바꾸는 것만으로 현재 부팅한
기기에 적용되는 것은 아니다. 후보/원본 비교 빌드에서 다른 설정은 유지한다.
DMS의 기존 OEM 추가 튜닝이나 저장 상태가 영향을 줄 수 있으므로 실제 사용
프로필/방향과 서비스 로그도 확인한다. 데이터 디렉터리를 임의 삭제하지 않는다.

## 측정 앱을 만들었나?

**별도 Android 측정 APK는 아직 작성하지 않았다.** 준비된 것은 다음 호스트 도구다.

- `make-channel-probe.py`: 750Hz의 짧은 L/R 분리 WAV와 구간 JSON 생성.
- `collect-audio-route.py`: ADB로 믹서·AudioFlinger·audio policy 등을 읽기만 한다.
- 두 도구 모두 앱을 설치하거나 소리를 자동 재생하거나 EQ를 적용하지 않는다.
- 채널 확인 WAV는 주파수 응답/왜곡을 측정하는 sweep가 아니다.

## 플래시 후 방향별 채널 매핑

1. 설치된 `/vendor/etc/dolby/dax-default.xml`의 SHA-256이 후보 해시인지 확인한다.
   Dolby service, 실제 SW effect·제어권 및 활성 profile을 확인한다. GEQ readback만으로
   optimizer 적용 여부를 입증하지 않는다.
2. 아래처럼 WAV를 생성한다. 기존 출력이 있으면 생성기가 덮어쓰기를 거부한다.

```sh
python3 tools/make-channel-probe.py /tmp/renoir-channel-probe.wav
adb push /tmp/renoir-channel-probe.wav /sdcard/Download/renoir-channel-probe.wav
```

3. 스피커를 가리거나 손으로 막지 말고 낮은 미디어 볼륨에서 파일을 수동 재생한다.
   1초 무음 → 0.5초 L → 1초 무음 → 0.5초 R → 1초 무음이다.
   각 구간에서 상단·하단 중 어디서 소리가 나는지 적는다. −36dBFS 파일 레벨은
   실제 소리 크기를 보장하지 않으므로 볼륨은 낮게 시작한다.
4. Dolby OFF/ON 각각 세로·가로 양방향에서 반복한다. 모노 오디오, player remix,
   balance 상태를 기록한다. ON에서 양쪽이 들리면 virtualizer의 혼합 가능성을
   남기고 단일 출력이라고 억지로 분류하지 않는다.
5. 음악 또는 probe 반복 재생 중 매번 새 디렉터리에 다음처럼 상태를 저장한다.
   4초 probe가 끝난 뒤 캡처하면 활성 playback을 놓칠 수 있다.

```sh
python3 tools/collect-audio-route.py /tmp/renoir-portrait-off
```

TFA Profile, Swap channel, PCM/offload 실제 경로 및 DAX 방향 선택과 물리 출력을
대조한다. 최초에는 마이크 동시 녹음 없이 채널을 확인한다. 같은 기기에서 녹음을
켜면 HAL의 재생/캡처 동시 처리 때문에 경로·채널 교환 정책이 달라질 수 있다.

## 음향 측정은 어떻게 하나?

**기본 청취 비교:** 동일 음원·볼륨·프리셋·위치에서 후보/원본의 소리,
치찰음·찌그러짐·떨림·음량 불균형을 비교한다. 이것은 청취 평가이며 주파수 응답
측정으로 기록하지 않는다. 즉시 이상이 있으면 해당 실험을 중지한다.

**객관적 비교:** 외부 마이크와 녹음 장치를 같은 고정 위치에 놓고, 별도의
저레벨 broadband/sweep 시험 신호로 후보와 원본을 각각 최소 3회 녹음한다.
각 방향에서 마이크·기기 거리와 볼륨을 똑같이 유지하고 배경 소음도 기록한다.
가능하면 재생 기기와 분리된 녹음 장치를 써서 HAL 경로 변경을 피한다.
한 방향의 측정을 다른 방향의 측정과 그대로 비교하지 말고 방향별 A/B로 비교한다.

분석은 채널별 주파수 응답, 반복 오차, 출력 clipping 및 왜곡을 본다. 주파수
응답용 sweep와 왜곡용 시험 신호/분석은 구분한다. 원시 녹음과 시험 신호를
함께 보관해야 다시 분석할 수 있다. 마이크 보정이 없으면 상대 변화까지만
판단하고 절대적인 평탄도·음압 보정이라고 주장하지 않는다.

내장 마이크만으로도 상대 비교를 시도할 수 있으나 AGC/NS·마이크 응답과 기구적
결합이 섞인다. 따라서 내장 마이크만 보고 자동 역보정하거나 저역 제한을 풀지
않는다. 이 녹음·sweep·FFT 측정 기능은 현재 제공한 도구에 아직 구현되어 있지 않다.
